# H2 — Evaluation Plan

**Статус:** предложение для лабы. Ничего ещё не измерено.
**Рядом:** [`SPEC.md`](./SPEC.md), [`PROMPTS.md`](./PROMPTS.md), [`README.md`](./README.md).
`CHECKS.md` / `RUN-PROTOCOL.md` появятся отдельно — сюда не тащить их содержимое.

Вопрос плана: **как понять, работает ли подмешивание целых сессий, и стоит ли это своих токенов.**

---

## 0. Четыре слоя, четыре разные вещи

Слово «eval» нельзя применять ко всему сразу. Слои ломаются в разных местах. Строить в этом порядке.

| слой | вопрос | имя | форма ответа |
|---|---|---|---|
| **L0** | прогон повторяется? | reproducibility | байт-идентичный `--replay` |
| **L1** | шаг держит контракт? | contract checks | pass / fail на файлах |
| **L2** | выход хорош против золота? | offline eval | метрики + бейзлайны |
| **L3** | где нет золота — судья | auto-eval | только калиброванные цифры |
| **L4** | этим пользоваться? | fitness for purpose | FIT / FIT WITH LIMITS / NOT FIT |

Три правила, без которых цифра — история:

1. **L1 не качество.** Зелёный контракт значит, что проводка жива. Не публиковать его как доказательство, что сессии помогают.
2. **L2 без бейзлайна — не результат.** `useful_hit = 0.41` ничего не значит, пока рядом нет B0 / B1 / oracle на том же хвосте.
3. **Разметку, пользу, ротацию и цену не склеивать.** Плохие теги — вина S2. Хорошие теги и пустой поиск — вина S3. Поиск жив, а в пакете одни и те же id — вина ротации. Польза есть, но пакет в 20 раз дороже карточки — отдельный вердикт по цене.

## 1. Что меряем, и на чём

До отдельного H2-пака можно брать H1 `data/` (та же схема диалога, SPEC §3). Золото H1 (`unlock_guideline`) **не** золото H2. Его нельзя подставлять в `problem_shape` и нельзя считать пользой пакета.

Два нужных файла разметки. `gold_tags` пишут люди. `gold_useful` на срезе корпуса —
по решению основателя 2026-08-28 агентная разметка `deepseek-v4-pro`, **NOT human gold**
(контракт: [`ROUND-0-PLAN.md`](./ROUND-0-PLAN.md)). Каждая цифра L2-пользы в отчёте
обязана нести пометку «agent-labeled gold — NOT human gold».

`data/gold_tags.jsonl` — теги сессии:

```json
{
  "dialogue_id": "d-001",
  "tags": {
    "problem_shape": "login fails after password reset",
    "constraint": "stale jwt cache",
    "ending": "resolved"
  }
}
```

`data/gold_useful.jsonl` — какие прошлые сессии были бы полезной подсказкой для этого query:

```json
{
  "query_id": "d-900",
  "useful_dialogue_ids": ["d-001", "d-014"],
  "notes": "same reset + stale session cookie"
}
```

Правила золота:

- `channel` и `vertical` в gold_tags не дублируют — они уже в диалоге.
- `useful_dialogue_ids` MUST указывать только на диалоги с более ранним `closed_at`, чем у query. Иначе это утечка в будущее, строка воид.
- Пустой `useful_dialogue_ids` разрешён: для этого query в прошлом нет полезной сессии. Тогда правильный ответ системы — пустой пакет или пакет, который не вредит. См. классы §4.2.
- Живой агент в v1 не нужен. Исход «помогло / навредило» выводится из пересечения пакета с `useful_dialogue_ids`. Это и есть лабораторный `source=gold` из SPEC S6.

Пока золота нет, L2 не публикуется. L0 и L1 живут на фикстурах.

## 2. L0 — повторяемость

- Одна команда на прогон, одна папка, один `manifest.json` (схему зафиксирует `RUN-PROTOCOL.md`, когда он появится).
- Детерминированные шаги S1, S3, S4, S5, S7 MUST давать байт-идентичный выход на тех же входах.
- Недетерминирован только S2. Фиксировать: `temperature=0`, текст из `PROMPTS.md`, model id, **сырой request/response на каждый диалог** в `raw/tag/<dialogue_id>.json`.
- `--replay <run_id>` MUST прогнать весь конвейер из сохранённых ответов S2 **без** новых вызовов модели. Метрики L2 MUST совпасть байт-в-байт.
- В `manifest.json` — sha256 входов, `PROMPTS.md`, конфига SPEC §6, каждого артефакта. Прогон без sha — воид.
- Симуляция случайного бейзлайна B1 MUST идти с фиксированным `--seed`.

## 3. L1 — контракт по шагам

Полный список id — в будущем `CHECKS.md`. Здесь — что именно нельзя прощать, потому что иначе L2 не про ту систему.

HARD (нарушение обнуляет прогон, метрики не публикуются):

| id | шаг | правило |
|---|---|---|
| `C-SELF` | S3/S5 | query не попадает в свои кандидаты и не уходит в свой пакет |
| `C-FUTURE` | replay | в пакет не попадает сессия с `closed_at` ≥ query |
| `C-PII` | S2 | после скроба в тегах и `turns` нет email / телефона / ≥10 цифр подряд / cvv/iban/ssn |
| `C-PROMPT` | S2/S5/S6 | система не дописывает свой system/user; пакет — шаблон `PROMPTS.md` §5 |
| `C-SIZE` | S5 | `len(packet) ≤ MAX_PACKET`, пустых слотов нет |
| `C-DELTA` | S7 | good/bad/unclear двигают только пары из пакета × `tag_key` query; чужие строки стоят |
| `C-REPLAY` | L0 | `--replay` без LLM и с теми же метриками |

SOFT (в отчёт, прогон жив):

- доля `reject` на S2;
- доля пустых кандидатов на S3;
- доля пакетов, где explore-слот совпал с топом по score (некому было взять);
- grounding: хотя бы одно слово ≥5 символов из `problem_shape` и не-`none` `constraint` есть в транскрипте.

## 4. L2 — четыре отдельные измерения

Не сворачивать в один score.

### 4.1 Разметка — S2 против `gold_tags`

Считать **три числа**, не одно «tag accuracy».

Нормализация перед сравнением: lowercase, схлопнуть пробелы, убрать знаки `«.,;:!?»`.

| метрика | как |
|---|---|
| `ending_exact` | совпал один из четырёх литералов |
| `constraint_exact` | совпал после нормализации |
| `problem_shape_exact` | совпал после нормализации |
| `problem_shape_jaccard` | Jaccard токенов ≥ 0.5; только второй сигнал, не замена exact |
| `tag_reject_rate` | доля сессий с пустым `problem_shape` после скроба |

На расхождениях `problem_shape` — выборка 30 штук для ручной ссылки (одинаковое смысло / разные смыслы). Это не метрика прогона, а комментарий к exact.

Если `ending_exact` низкий — ранкер не трогать: он ищет не туда.

### 4.2 Польза пакета — главная метрика эксперимента

На query с готовым `gold_useful` строится пакет из **уже лежащего** пула (порядок replay из SPEC §8).

`useful_hit` — в пакете есть хотя бы одна сессия, чей `source_dialogue_id` есть в `useful_dialogue_ids`.

**Золото пользы на срезе — агентное** (`deepseek-v4-pro`, решение основателя 2026-08-28),
**NOT human gold**. Оно судит по транскрипту (переносимый ход), не по `unlock`/`unlock_guideline`
(это перемерило бы H1). Любая цифра этого раздела в отчёте обязана нести пометку
«agent-labeled gold — NOT human gold». Контракт: [`ROUND-0-PLAN.md`](./ROUND-0-PLAN.md).

Каждый query попадает ровно в один класс:

| класс | условие | зачем |
|---|---|---|
| `hit` | пакет непустой и `useful_hit` | выигрыш |
| `wrong` | пакет непустой и нет ни одной полезной сессии | **вред** — агенту отдали чужой ход |
| `abstain` | пакет пустой | тишина, без вреда |

`hit + wrong + abstain = 1.0`.

`wrong` в рубрике fitness весит **больше**, чем `abstain`. Лучше промолчать, чем подсунуть чужую целую сессию.

Для замкнутого контура S6/S7 лабораторный исход выводится так:

| класс пакета | `outcome` для S7 |
|---|---|
| `hit` | `good` |
| `wrong` | `bad` |
| `abstain` | `unclear` |

Так рейтинг учится на том же сигнале, которым меряем пользу. Живого агента для этого не нужно. Режим `--source llm` в L2 **не входит**.

### 4.3 Бейзлайны — обязательно, тот же хвост, тот же код подсчёта

| id | что делает | что доказывает |
|---|---|---|
| **B0** | пакет всегда пустой | пол: метрика не срабатывает «на ничём»; все query — `abstain` |
| **B1** | из кандидатов S3 берёт `MAX_PACKET` случайных, без рейтинга и ротации; seed фиксирован | **главный бейзлайн** — даёт ли ранкер что-то сверх случайной похожей сессии |
| **B2** | топ по `score` **без** explore-слота | цена ротации: насколько `hit` теряем, чтобы не залипнуть |
| **B3** | oracle: в пакет кладутся до `MAX_PACKET` id из `useful_dialogue_ids`, если они уже в пуле | потолок поиска+пула; если B3 низкий — виноват данные, не ранкер |
| **T** | полный контур S3–S5 с ротацией | treatment |

Интерпретация, зафиксированная **до** прогона:

- **T ≤ B1 по `hit`** → ранкер не добавляет ничего сверх случайной похожей сессии. Это результат. Не лечить порогами.
- **T > B1 по `hit` и T.`wrong` ≥ B1.`wrong`** → ранкер чаще попадает и чаще вредит. В отчёт идут оба числа, вердикт см. §6.
- **B3.`hit` < 0.50 на query, у которых `useful` непустой** → в пуле к моменту query нет золотых сессий. Это потолок данных, его писать в `audit.json` до сравнения ранкеров.
- **B0.`hit` ≠ 0** → сломан подсчёт, прогон выбросить.

Сравнение с H1-карточками в этот прогон **не входит**. Это другая гипотеза и другой пакет. Цену карточки можно упомянуть в §4.5 как ориентир, не как руку T vs H1.

### 4.4 Поиск S3 — отдельно от ранкера

На тех же query:

| метрика | как |
|---|---|
| `retrieve_recall` | доля золотых `useful`, которые уже лежат в пуле **и** прошли S3 |
| `retrieve_empty` | доля query, у которых в пуле есть хотя один useful, а кандидатов 0 |
| `retrieve_noise` | доля кандидатов с пересечением тегов < `TAG_FIELDS_MIN` — должна быть 0, это ещё и L1 |

Если `retrieve_empty` высокий при живом B3 — ломается S3 (или разметка), не S4.

### 4.5 Ротация — не польза, отдельный счёт

Считать на длинном replay после того, как в пуле уже есть кому выбирать. Первые N query, где кандидатов < `MAX_PACKET`, в эту сводку не мешать — отрезать порогом `ROTATION_BURN_IN` (число в `audit.json`, не в конфиге ранкера).

| метрика | как |
|---|---|
| `unique_served` | сколько разных `session_id` хотя раз ушли в пакет |
| `top1_share` | доля всех слотов пакетов, которую занял один самый частый id |
| `top3_share` | то же для трёх самых частых |
| `explore_fill` | доля пакетов, где последний слот ≠ тот, который был бы третьим по score |
| `explore_promote` | сколько сессий, которые сначала попали в explore, а потом оказались в exploit-слотах |
| `decay_fired` | сколько раз S7 срезал score по `DECAY_EVERY_SHOWS` |

Главный сигнал залипания — `top1_share` и `top3_share`. Если на длинном хвосте три id занимают больше половины слотов — ротация не сработала, даже если `hit` красивый.

B2 рядом нужен именно здесь: сравнить `top1_share(T)` с `top1_share(B2)` и `hit(T)` с `hit(B2)`.

### 4.6 Цена

Целая сессия в промпте — главный риск идеи. Даже без живого агента считаем токены, как будто пакет ушёл в модель.

Записывать в `cost.json`:

| поле | что |
|---|---|
| `tag_calls` | число вызовов S2 |
| `tag_tokens_in` / `tag_tokens_out` | сумма по S2 |
| `tag_usd_per_1000` | USD на 1000 диалогов разметки |
| `packet_tokens_p50` / `p95` / `max` | токены `packet_text` (шапка + целые `turns`) |
| `packet_tokens_per_query_mean` | среднее по query с непустым пакетом |
| `implied_agent_usd_per_1000` | `packet_tokens` × цена входа той же модели, что на S2; это **оценка**, не факт живого вызова |
| `tag_latency_p50` / `p95` | только S2 |
| `serve_latency_p50` / `p95` | S3+S4+S5 без LLM |

Ориентир, не метрика прогона: типичная H1-карточка ~30–40 слов. В отчёт писать `packet_tokens_p50 / 40` как грубый множитель «насколько целая сессия дороже карточки». Сравнивать пользу H1 и H2 нельзя этим числом.

Токены считать одним способом на всё плечо: либо тикер провайдера из raw S2, либо `len(text)//4` как fallback. Способ MUST быть записан в `cost.json`.

## 5. L3 — судья, только где нет золота

В v1 судья **не заменяет** `gold_tags` и `gold_useful`. Он нужен, если золото покрывает только часть корпуса.

Два узких случая:

1. **Разметка без полного gold_tags.** Выборка 40 сессий. Судья отвечает: теги верны / выдуманы / есть PII. Модель судьи MUST отличаться от модели S2.
2. **Исход `--source llm`.** Качество хелпера из `PROMPTS.md` §6 мерять на выборке, где уже есть `gold_useful`. Цифру не смешивать с L2.

Калибровка: 20 из 40 размечает человек. Согласие судьи с человеком < 0.7 → цифры **uncalibrated**, в §6 не входят.

В первом проходе L3 можно не открывать, если золото на разметку и на useful-пары уже есть.

## 6. L4 — fitness for purpose

Не метрика. Рубрика после L1–L2 (и L3, если он был).

### 6.1 Hard gates (любой провал = NOT FIT)

| gate | порог |
|---|---|
| `C-SELF`, `C-FUTURE`, `C-PII`, `C-PROMPT`, `C-SIZE`, `C-DELTA`, `C-REPLAY` | все hold |
| B0.`hit` | `== 0` |
| подсчёт классов | `hit + wrong + abstain == 1` |

### 6.2 Value gates (провизорные, см. §7)

| gate | порог | зачем |
|---|---|---|
| `ending_exact` | ≥ 0.80 | иначе поиск идёт не по той оси |
| `constraint_exact` | ≥ 0.60 | второе поле тега |
| `problem_shape_exact` | ≥ 0.35 **или** `problem_shape_jaccard` ≥ 0.60 | свободный текст, exact один не вытянет |
| T.`hit` | **> B1.`hit`** на том же n | ранкер должен бить случай |
| T.`wrong` | ≤ 0.25 | чужая целая сессия — дорогой вред |
| `retrieve_empty` | ≤ 0.20 среди query, где useful уже в пуле | иначе ранкер не виноват |
| `top3_share` | ≤ 0.55 после burn-in | иначе выдача застыла |
| `explore_fill` | ≥ 0.15 там, где кандидатов > `MAX_PACKET` | слот ротации не мёртвый |

### 6.3 Cost gates

Жёсткого порога USD в v1 нет — сначала увидеть распределение (§7 A6). В отчёт MUST войти все поля §4.6.

Мягкий флаг, не hard-fail: если `packet_tokens_p50` > 1500, в вердикте обязательна строка «целая сессия дорогая; следующий рычаг — нарезка, см. SIMPLIFICATIONS». Это не отменяет FIT по пользе, но не даёт тихий FIT без оговорки о цене.

### 6.4 Вердикт — ровно одна из трёх строк

- **FIT** — hard gates зелёные, value gates зелёные, цена записана. Если `packet_tokens_p50` > 1500 — не FIT, а FIT WITH LIMITS с этим флагом.
- **FIT WITH LIMITS** — hard зелёные, один или больше value/цена не прошли; назвать каждый промах, цифру и самый тонкий рычаг (разметка / `TAG_FIELDS_MIN` / ротация / нарезка сессии).
- **NOT FIT** — упал hard gate, или T.`hit` ≤ B1.`hit`. Назвать, с цифрой.

Пороги §6.2 менять **только до** полного прогона и только после аудита §7, с причиной в этом файле. Править порог после увиденного числа нельзя.

## 7. Аудит пола и потолка — до полного прогона

Не мерить систему о недостижимую планку. Каждый пункт — минуты арифметики на уже имеющихся диалогах и золоте. Писать в `audit.json`.

| id | вопрос | если срабатывает |
|---|---|---|
| **A1** | Какая доля query имеет ≥1 useful-сессию с более ранним `closed_at`? Это потолок `hit` у oracle B3. | Если < 0.30 — ганать `hit` не про ранкер, а про дыры в gold/корпусе. Или дорасти gold, или снизить ожидание **до** прогона, с цифрой здесь. |
| **A2** | Какая доля золотых пар (query, useful) разделяет меньше `TAG_FIELDS_MIN` полей, если расставить **золотые** теги? | Если > 0.20 — S3 по конструкции теряет каждую пятую полезную пару. Снизить `TAG_FIELDS_MIN` или признать, что схема тегов слишком дробная. Не трогать ранкер. |
| **A3** | Сколько уникальных `tag_key` на gold_tags? Медиана размера корзины? | Если почти все ключи уникальны — рейтинг «под tag_key» не накопится. Это находка про схему, не про S7. |
| **A4** | На хвосте корпуса какая доля query имеет больше `MAX_PACKET` кандидатов при золотых тегах? | Если < 0.20 — explore-слот почти некому взять, гант `explore_fill` недостижим. Снять его с value gates **до** прогона. |
| **A5** | Покрытие gold: сколько диалогов с тегами, сколько query с useful-списком, сколько из них с пустым списком. | Если useful-пар меньше 40 — L2 по пользе не публиковать, только L0/L1 и разметку. |
| **A6** | Медиана токенов одного транскрипта × `MAX_PACKET`. | Это честный потолок `packet_tokens_p50`. Записать рядом с флагом 1500 из §6.3. |

`ROTATION_BURN_IN` = первый индекс query, после которого доля query с ≥ `MAX_PACKET` кандидатами стабильно выше 0. Записать число, не подбирать его под метрику.

## 8. Матрица моделей

LLM в измеряемом контуре один — S2. Всё ниже детерминировано. Разница между моделями — это разница разметки.

Первый проход — одна рука, как в H1. Вторую модель не выдумывать.

| слот | модель | статус |
|---|---|---|
| `tag` | **`deepseek-v4-flash`** | по умолчанию та же, что H1 pass 1; можно сменить флагом, не правкой |
| `judge` | не назначена | только если откроется L3 |

Имя модели, ключ и endpoint в код не зашивать.

## 9. Стадии

Не гнать 1000 диалогов, чтобы найти дыру в upsert.

| стадия | данные | зачем | гейт дальше |
|---|---|---|---|
| **S0 smoke** | 10–20 фикстурных диалогов | проводка S1–S7, HARD, replay | все HARD зелёные |
| **S1 dev** | 80–150 диалогов + кусок gold | считаются метрики, аудит A1–A6 | `audit.json` записан, пороги достижимы или поправлены здесь |

| **S3 judge** | только если не хватило золота | L3 | калибровка или явно `uncalibrated` |
| **S4 verdict** | всё выше | рубрика §6.4 | одна из трёх строк |

Золото useful-пар **замораживать** до S2. Дорастивать пары после увиденного `hit` нельзя.
