# Close-out report — H2v2: категориальная разметка и подмешивание сессий

Дата: 2026-08-29. Каталог: `standalone/h2v2-categorical-scoped-memory`.

Этот документ — человеческое резюме эксперимента: что мы проверяли, как проверяли,
что показали цифры и что мы считаем доказательством.

---

## Гипотеза

Мы проверяли простую идею: если **разметить каждую завершённую сессию** коротким
набором метаданных (главное — «какая это процедура»), а потом **подмешивать похожие
прошлые сессии целиком** в новый диалог как подсказку агенту — это помогает агенту
отвечать лучше, чем совсем без подсказки.

Гипотеза распадается на два независимых вопроса:

1. **Полезен ли сам сигнал** — помогает ли подмешанная похожая сессия против пустого пакета?
2. **Нужен ли «умный» ранкер** — добавляет ли обучающийся выбор (рейтинг по исходам)
   что-то сверх случайного выбора из найденных похожих сессий?

Ответ на первый вопрос — **да** (см. ниже). Ответ на второй — **пока нет**.

---

## Подход (как проверяли)

1. Взяли корпус поддержки (ABCD) и срез из **60 реальных вопросов**.
2. Разметили все сессии тегом-категорией «процедура» — закрытый словарь **~30 id**.
   Это единственный вызов LLM в контуре (`deepseek-v4-flash`, temperature 0).
   Метка `unlock` из исходных данных тегеру **не подавалась** — категория выводится
   только из транскрипта.
3. Для каждого вопроса: поиск кандидатов = точное совпадение категории; пакет = до 3
   прошлых сессий.
4. Сравнили **5 «рук»** на одном подсчёте hit / wrong / abstain:
   - **B0** — всегда пустой пакет (пол),
   - **B1** — случайные кандидаты из найденной ячейки (главный соперник),
   - **B2** — топ по рейтингу, без ротации,
   - **B3** — оракул: всегда полезные (потолок),
   - **T** — полный контур (рейтинг + ротация).
5. «Полезность» определялась по заранее размеченному золоту (агентная разметка
   `deepseek-v4-pro`, **не** человеческая).

## Результаты (цифры)

### Поиск — это ключевое улучшение относительно v1

| метрика | v2 | v1 (для сравнения) |
|---|---|---|
| recall по золоту | **0.81** (потолок оракула 1.00) | recall 1.0 был тривиальным (весь пул — кандидаты) |
| медиана кандидатов на вопрос | **10** | 320–380 |
| вопросов без кандидатов | **0** | — |

В v1 метки-константы пропускали весь пул, и поиск не фильтровал. В v2 тегер по
транскрипту восстанавливает правильную категорию — и поиск стал настоящим фильтром.

### Руки на 60 вопросах (hit / wrong / abstain)

| рука | hit | wrong | abstain |
|---|---|---|---|
| B0 (пусто) | 0 | 0 | 60 |
| B1 (случайно из ячейки) | **38** | 22 | 0 |
| B2 (топ по рейтингу) | 37 | 23 | 0 |
| B3 (оракул) | 46 | 0 | 14 |
| T (полный контур) | **38** | 22 | 0 |

Цена пакета: медиана ~819 токенов (ниже порога 1500 — пакет дешёвый).

### Как читать таблицу «руки» (что значат B0–B3 и T)

**Важно:** это **60 тестовых вопросов**, а не один чат. Для каждого вопроса система
собирает пакет (до 3 прошлых сессий) и подмешивает его. Числа в таблице — это
**«в скольких из 60 вопросов получилось»**, а не «сколько сессий взяли».

**Что такое «hit»:** попадание — в пакете оказалась хотя бы одна сессия, которую золото
заранее пометило как полезную именно для этого вопроса.

> `hit` измеряет попадание правильной подсказки в пакет, а **не** качество итогового
> ответа агента. End-to-end эффект на ответы в этом прогоне не мерили (нужен отдельный
> судья качества ответов). Мы доказываем, что механизм находит и подмешивает нужную
> сессию — это необходимое условие пользы, но не само измерение ответа.

Пример. Вопрос: «как отчистить жвачку с подошвы ботинка». В памяти 320 сессий, из них
~10 про ботинки (ячейка «boots»). Золото говорит: среди них 2 сессии, где агент реально
показывал процедуру чистки. Подмешали одну из этих 2 → **hit**. Подмешали другую про
ботинки (например, про размер) → **wrong**.

**Все руки работают с тегами** — разница только в том, КАК выбираются сессии из найденной
ячейки:

| Рука | Стратегия выбора | Смысл |
|---|---|---|
| **B0** | всегда пустой пакет | «пол» — контроль: без подсказки попаданий 0 |
| **B1** | 3 случайные сессии из ячейки | «просто похожая сессия» — главный соперник |
| **B2** | 3 сессии с высшим рейтингом из ячейки | рейтинг без ротации |
| **B3 (оракул)** | напрямую сессии, помеченные золотом как полезные | «чит» — потолок: сколько вообще достижимо |
| **T** | полный контур (рейтинг + ротация) | наша система |

Итог по 60 вопросам: B1 = 38, B2 = 37, T = 38, B3 = 46 (у 14 вопросов полезной сессии
нет вовсе — поэтому оракул по ним «abstain»). Все «умные» способы дают столько же,
сколько случайный выбор из правильной ячейки (38). Значит, **всю работу делает ячейка
(категория), а ранкер ничего не добавляет**.

---

## Что мы считаем доказательством

Доказательство пользы — это **три числа, которые держатся только вместе**:

1. **Материал есть**: оракул B3 = 46/60 — в 46 из 60 случаев в пуле лежала реально
   полезная прошлая сессия (в 14 — полезной сессии для вопроса не существует вовсе).
2. **Поиск её находит**: recall 0.81 при медиане 10 кандидатов — тегер по одному
   транскрипту попадает в правильную категорию, без подсказки `unlock`.
3. **Подмешивание помогает**: случайный выбор из правильно найденной ячейки даёт
   **38/60 hit (0.63)** против **0** у пустого пакета.

**Формулировка доказательства:** подмешивание целой прошлой сессии даёт ощутимый
прирост полезности — с 0 до 0.63 hit — при условии, что поиск по категории работает
(recall 0.81). Прирост не зависит от ранкера (T = B1, см. ниже), то есть эффект идёт
от **разметки и поиска**, а не от обучающегося выбора. Если хотя бы один из трёх
пунктов падает — доказательства нет.

---

## Следующий шаг — ранкер (коротко)

Вторая часть гипотезы — «обучающийся ранкер выбирает лучше случайного» — на этом срезе
**не подтвердилась**: T = B1 = 38/60 (ровно поровну). Как только поиск нашёл правильную
ячейку, внутри неё почти все сессии полезны, поэтому выбор ничего не добавляет.

Но гипотеза ранкера **не закрыта**: на 60 запросах рейтинг не успевает накопиться
(30 ячеек → ~2 запроса на ячейку). Потенциал есть там, где ячейка широкая (например,
`product_spec` собирает 30/320 сессий) или где полезность внутри ячейки неоднородна.
Это отдельный прогон, а не правка этого вердикта.

---

## Оговорки

- Золото полезности — агентное (`deepseek-v4-pro`), **не** человеческое.
- Словарь (~30 процедур) покрывает срез; полный домен шире (96 уникальных `unlock` в полном пуле).
